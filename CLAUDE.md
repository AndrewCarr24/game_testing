# game_testing

Modern tech-billionaire mansion game. Current phase: building game-ready assets in Blender (driven over the `blender` MCP server, see `.mcp.json`).

## Asset pipeline
- Every asset is a generator script: `blender/assets/<name>.py`, parameters in a `P` dict at the top, `build(**overrides)` rebuilds its collection from scratch. Run in Blender with
  `ASSET = "<name>"; exec(open("/Users/andrewcarr/Documents/projects/game_testing/blender/run.py").read())`.
  Change the script, not the .blend, so work stays reproducible. The working Blender file is `blender/levels/mansion.blend`.
- Shared helpers: `blender/lib/common.py` (cushions, bent tubes, bevels, box UVs, glTF export), `blender/lib/textures.py` (numpy-generated tileable maps → `assets/textures/`).
- Conventions: metres, origin at floor centre, front faces -Y, root empty named after the asset, parts named `<Asset>_<Part>`. Principled BSDF + image textures only (what glTF carries). UV scale = world scale (wood 0.5 m tile, leather 0.2 m tile).
- Export: `common.export_glb(root, "assets/models/<name>.glb")`. Check in engine: `python3 -m http.server 8765` from the project root, open `http://localhost:8765/viewer/?asset=<name>` (three.js 0.160, same stack as ../video_game).

## Levels (the house)
- `blender/levels/plan.py` is the floor plan as data: rooms (rect, level, kind, double height), OPEN ring corners, CUTS (openings with optional door asset + swing + lock, windows, balustrades, garage door) on wall lines, the floating STAIR, SPAWN. Main house ~52 x 40 m, two floors (ground 0, upper +4.6 m; ceilings 4.2 / 3.8; double-height entry and great room to 8.4 m), courtyard 20 x 14 m ringed by 3.5 m galleries. Future wings attach through the facades (x = ±26, y = ±20).
- `blender/lib/house.py` generates the shell from the plan: per-room floor/ceiling slabs and 0.15 m wall linings (each room owns its side, so finishes are per room), cuts through every lining on a cut's line, glazing, rails with 2.2 m invisible colliders, the stair, then `merge()` joins it into one mesh per (room, material).
- `blender/levels/rooms/<room>.py` dresses a room (interface at the top of `mansion.py`): FINISHES, PLACEMENTS and LIGHTS in room-local metres ((0, 0) = interior centre, z = floor), optional PROBE. `python3 blender/levels/room_info.py <room>` prints a room's interior, doors and windows in those coordinates.
- `blender/levels/mansion.py` builds plan + rooms + props and exports `assets/models/mansion_shell.gltf`, a `.gltf` per prop, `assets/levels/mansion.json` (rooms with probe/rect/floor, props with their room, colliders, lights, spawn). Missing asset modules are skipped (SKIP).
- Build headless (the Blender window is never needed): `Blender -b --factory-startup --python blender/tools/build_level.py -- [--plan] [--room R] [--only-room R] [--no-export --no-save]`; `--plan` renders top-down plans, `--room R` a 4-view interior sheet (`build/previews/`). Without `--no-export --no-save` it writes the shared level and saves `blender/levels/mansion.blend` (what the bake reads).
- Tests read positions from the level file (`viewer/tools/level.mjs`); run them in place after `npm install --no-save playwright-core`.
- Viewer: `viewer/?level=mansion` (click to play; WASD, Shift run, Space jump, C crouch, E interact, I inventory; `&pos=x,y,z&look=x,y,z` sets the eye position/view; `&bake=0` unbaked; `&tm=neutral|agx|aces` tone mapping, default Neutral).
- Collision: each prop gets one box per mesh part (`common.part_colliders`, skipping trim, wall fixtures and moving parts). Player: `viewer/player.js` (box character, gravity, ~1 m jump, 0.3 m step-up so stairs work, lands only on what's under it). Stress test: `viewer/tools/walls.mjs` must report 0 impossible positions.
- Crouch is C, not Cmd/Ctrl: Cmd+W / Ctrl+W close the tab and can't be blocked, and macOS drops other keys' keyup while Cmd is held.

## Grounds (outdoors)
- `plan.GROUNDS`: lawn (to x ±90, y ±80), stone terrace ringing the house (to x ±31 / y ±25), perimeter hedge (x ±70, y ±62, drive gap at x 14..25.5 south) and 10 ZONES (rect + triangle budget, ~70k for the estate). Each zone is dressed by `blender/levels/outdoor/<zone>.py` (`PLACEMENTS` in zone-local metres: (0, 0) = rect centre, z = 0 = lawn = world `plan.LAWN_Z` -0.08) with assets `blender/assets/<prefix>_*.py`; trees/shrubs are `plant_*` (planting zone). Briefs: `specs.md` "## Grounds"; agent instructions: `prompts/build_zone.md`; preview: `build_level.py -- --no-export --no-save --zone <zone>`.
- `blender/levels/grounds.py` builds the lawn / terrace / hedge as grids (vertex-lighting resolution), places every zone as world-space copies, splits by material and merges into ~8 meshes (`Mansion_Outdoor_Flat` = every untextured material, one per textured palette material, Water, Glass) -> `assets/models/mansion_outdoor.gltf`. Outdoor materials only from `blender/lib/outdoor.py` (untextured colours are free; textured = stone, teak, foliage, grass, gravel; `water()`, `glass()`).
- Lighting: `bake.py` bakes the outdoor meshes into a "Bake" vertex-colour attribute (flat: colour x light; textured: light) and re-exports the outdoor gltf; `mansion_bake.json` "outdoor" holds the scales. Engine (`viewer/sky.js` `applyOutdoor`): unlit MeshBasicMaterial (vertex colour x scale x texture), no shadows or lights; water is a cheap sky-reflecting shader; lawn gets world-space mowing stripes.
- Beyond the hedge: `blender/levels/horizon.py` renders the horizon band (tree belts, fields, hills, haze) -> `T_Mansion_Horizon.webp` + `mansion_sky.json`; `viewer/sky.js` draws a procedural sky dome with the band over it (drawn after opaque geometry).

## Interactables
- A moving part is its own empty (pivot/origin where it rests) with an `interact` custom property, written to glTF extras (`export_extras=True`) → three.js `userData.interact`, so every placement of the asset gets the behaviour with no level changes. Types: `slide` (drawer: axis, distance), `rotate` (door: axis through the empty's origin, angle), `pickup` (keycard: item, name). Shared fields: duration, range (to the item's nearest edge), prompt/promptActive, side, `collide` (moving collider, solid only once settled), `indicator` (status-light node).
- State lives in the level, not the asset: `PLACEMENTS` options `lock` (item id the interactable needs) and `attach` (parent to another placement's node, e.g. the keycard inside `Desk_Drawer`). A pickup inside another interactable can only be taken while that one is open.
- Engine: `viewer/interactables.js` (`Interactables`, `Inventory`), `viewer/items.js` (`Hand` shows the armed item, `Throwables` arcs + glass shatter), HUD in index.html. Controls: I inventory (↑/↓ arrows choose, Enter arm), Enter use armed item, Delete/Backspace put away. Keys (keycard) only work armed: Enter at a door with that lock toggles locked. Throwable pickups (`"throwable": true`) are thrown with Enter. Tests: `viewer/tools/drawer.mjs`, `keycard_door.mjs`, `throw.mjs`, `tour.mjs` (hall → bedroom), `movement.mjs`, `inventory.mjs`, `walls.mjs` (640 runs into every wall/corner/door; must report 0 impossible positions).

## Baked lighting
- `blender/levels/bake.py` (headless: `Blender -b blender/levels/mansion.blend --python blender/levels/bake.py -- mansion 1024`, ~30 min; lightmaps are denoised with Open Image Denoise) bakes, per room, Cycles diffuse lighting for the shell meshes tagged with that room into `assets/textures/T_Mansion_<Room>_Lightmap.webp` and a 360° panorama from the room's probe (sun hidden, highlights clamped) into `T_Mansion_<Room>_Env.webp` (8-bit sRGB of radiance / 3), bakes the grounds into vertex colours, and writes `assets/levels/mansion_bake.json`. Save the .blend first; re-bake whenever the layout changes.
- The lightmap atlases are generated in `mansion.py` (`common.lightmap_uv`, one 1024 atlas per room); sun, sky, exposure live in its `P`; ceiling strips and lamp lights are added per room and feed the bake.
- Engine (`viewer/baked.js`): lightmapped shell materials (cloned per room) take all direct light from the bake (real-time direct light off). Props get diffuse light from their room's order-2 spherical-harmonics probe (`sh` in the bake JSON, computed from the unclamped panorama so ceiling strips light the furniture like the walls) plus the real-time sun, and reflections from the room's highlight-clamped panorama. The bake also denoises lightmaps (mask-aware blur inside UV islands). `?bake=0` shows the old unbaked lighting for comparison.

### When to bake (rules)
- Don't bake after every change. Only changes to light need a bake: the shell (walls, windows, openings), ceiling strips and lamp lights, sun/sky, or new geometry that casts shadows or bounces light (furniture placement counts only for the room it's in; the grounds for the outdoor bake). Props' look, gameplay, UI and engine changes never need one.
- While iterating, use the cheapest bake that answers the question: the unbaked view (`&bake=0`) for layout; outdoor-only (~10 s) for grounds changes; the rooms that changed only; or a draft bake at 64 samples (~8 min for the whole house).
- The full 1024-sample bake (~30 min) runs once before committing or pushing, or when the user is away. Batch changes into one full bake; ask before starting one while the user is waiting.

## Web performance budget (it ships as an online three.js game)
- Baseline (2026-10-17, `viewer/tools/budgets.json`): 13.3 MB download (433 files, Draco geometry, WebP), ~276 draw calls mean / 657 peak (frames that redraw the shadow map), 501k triangles peak, ~210 MB GPU textures incl. lightmaps and env maps; M4 Pro at 2400x1350: ~550 fps, GPU 1.3 ms p50 / 2.1 ms p95; SwiftShader (no GPU) at 1280x720: ~4 fps.
- What keeps it there (all automatic): `viewer/batching.js` merges each room's static, opaque props into one mesh per material and `RoomCuller` skips furniture in rooms > 18 m away (shell, galleries and courtyard always draw); shell merged per room+material (`house.merge`); `common.export_gltf` Draco-compresses geometry; `blender/tools/optimize_textures.py` (run by build_level) shrinks prop textures to 512 (shell textures stay 1024); lightmaps 512 except the big volumes (1024).
- Never add real-time lights per room in the engine: one RectAreaLight per ceiling strip took the house to 3 fps. All interior light is baked.
- Measure: `viewer/tools/perf.mjs <url>` (unique download, draw calls, texture MB) and `viewer/tools/fps.mjs <url> metal|swiftshader W H DPR` for quick checks.

## Quality loop (better looks at the same cost)
The goal is more realism without more compute: `budgets.json` is a cost ceiling (the baseline plus a noise allowance), and the screenshots are what improves. The user judges looks.
- `node viewer/tools/bench.mjs <label>`: a scripted run at run speed through the house (`bench_route.mjs`: entry, galleries, great room, dining, kitchen, stair, upper galleries, office; ~53 s, uncapped frames) on two profiles, `gpu` (Metal, 1600x900 DPR 2) and `soft` (SwiftShader 1280x720, a stand-in for weak hardware). It records per-frame frame/GPU (timer query)/CPU time, draw calls and triangles, plus load time, download and texture MB, and per-room p95. Output goes to `build/bench/<label>/stats-<profile>.json`, a PASS/FAIL per budget and a line in `bench_history.jsonl`.
- `node viewer/tools/shots.mjs <label>`: 32 fixed views (a wide view per room and hero-prop close-ups), HUD hidden. They are deterministic (0% diff between identical runs).
- `node viewer/tools/compare.mjs baseline <label>`: a metrics table against the budgets, plus per-view pixel diffs, written to `build/bench/<label>/compare.html` (space = before/after, D = diff heatmap, arrows = views).
- Loop: make one change, then run shots, bench and compare, then show the user compare.html. Keep the change only if no budget is OVER and the user likes it; otherwise revert it. The deterministic counts and SwiftShader timings are the real gate; M4 timings are within ~5-10% noise. Re-baseline (and update budgets.json) only on purpose.
- Offline work is free by construction (bake samples/denoise, texture generation at the same resolution, geometry at the same triangle count); runtime changes must pass the budgets.

## Building assets in parallel
- `blender/tools/build_asset.py` builds one asset in its own headless Blender (`Blender -b --factory-startup --python blender/tools/build_asset.py -- <asset> [--no-export]`, ~2-7 s): report with budget WARNs, `.gltf` export, preview sheet at `build/previews/<asset>.png`. Safe to run several at once; never touches the open Blender window.
- Sub-agents get `prompts/build_asset.md` plus one entry from `specs.md` (status DRAFT → READY once the user has answered its open questions). They create only `blender/assets/<asset>.py`; placing assets in a level, engine features and commits stay with the orchestrator.
